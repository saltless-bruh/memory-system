### F2 · The governance gate fails today, and nothing runs it · `OPEN`

**Measured 2026-09-15:**


proves it by reading the policy table — which the served surface never consults
(F1). The claim is true, by accident rather than by the evidence cited.

**Flaw.** `mcp_policy.py:16` states the invariant: *"every command in the

### PEP 723 dissolves the skill-packaging blocker

A skill script declares its own dependencies inline; `uv run` builds an ephemeral
environment. The page checker keeps `yaml` and installs nothing permanently.

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.12"
# dependencies = ["pyyaml>=6"]
# ///
```

Anthropic's Claude Code guidance: *"Global package installation discouraged:
Skills should only install packages locally."* Neither a vendored YAML parser
nor a generated stdlib-only checker is required.

**Boundary.** On the Claude **API** surface, skills run sandboxed with no network
access and no runtime package installation, so a PEP 723 script fails there.
SNP's skills run in Claude Code / OpenCode against a checkout. Fine here, not
universal.

### Agent Skills — three corrections to "archify-style"

| | archify | the spec |
|---|---|---|
| script directory | `bin/` (a Node `package.json` convention) | **`scripts/`** |
| SKILL.md body | 137 lines | **under 5k tokens** |
| `name` | free-form | ≤64 chars, lowercase letters/digits/hyphens |
| `description` | long | ≤1024 chars; must state **what** and **when** |

The authoritative cost model, which is the case for skill-over-tool:

```
  LEVEL       WHEN LOADED          COST
  1 metadata  always, at startup   ~100 tokens per skill
  2 SKILL.md  when triggered       under 5k tokens
  3 scripts   run via bash         ONLY THE OUTPUT enters context
  3 refs      when read            zero until accessed

  an MCP tool definition:  100-500 tokens, every agent, every turn
```

### What archify actually contributes

Beyond `bin/`, five mechanisms worth copying:

1. **Zero runtime dependencies achieved at build time.** Every import in
   `bin/`, `renderers/`, `delta/` is a `node:` builtin; no `node_modules` exists.
   `ajv` is a devDependency that generates a 431 KB validator, which is
   committed.
2. **One schema is the source**; the checker is generated from it.
3. **`--check` is the drift guard**, run by the test suite. SNP already owns this
   shape in `export_agent_bundle.py --verify`.
4. **The receipt names its own scope** —
   `{schemaVersion, ok, command, type, input, checks:[{name, ok, details}]}` —
   and SKILL.md makes the check *count* part of the verdict: *"A receipt with
   only 4 artifact checks is basic validation, never showcase acceptance."*
   This is the direct antidote to `7 pages · 0 errors · PASS` that never says
   which tree.
5. **Progressive disclosure is enforced in prose**: *"Do not read … renderer
   source, validator source, tests … before the first candidate."*

**And the contract-copy count.** archify has one contract:
`schemas/*.schema.json`. SNP has **four** statements of one contract — the
vault's `SCHEMA.md` (prose), `REQUIRED_FRONTMATTER` in `scout/vault.py`,
`AGENTS.md` §4's heading frame (prose), and `snp-verify-vault/SKILL.md`'s
checklist (prose). None generated from another.

### SEP-986 — confirmation, correction, vindication

**Confirmed.** Status is **Final**, Standards Track. The C1 citation is accurate
as to status.

**Correction 1.** The SEP page carries its own warning: *"preserved as a
historical record… Changes made to the protocol after finalization are not
reflected here. Refer to the current specification."* SEP-986 says 1–64
characters; the live 2026-07-28 spec has moved. The authority is the spec, not
the SEP.

**Correction 2.** SEP-986 does not say what C1 attributes to it. Its entire
normative text on the subject is:

> Tool names SHOULD be unique within their namespace.

It never defines the namespace, never mentions server prefixing, and never
addresses cross-server collision. C1's conclusion may be right; it is C1's, not
the spec's.

**Vindication.** The backwards-compatibility clause reads:

> Existing **non-conforming** tool names SHOULD be supported as aliases for at
> least one major version, with a deprecation warning.

It is scoped to names that violate the *format*. `scout_wiki_search` and
`snpmemory_wiki_search` both conform, so **no alias obligation applies** to this
rename. The decided path — delete the stdio server, free the name, cross over by
ordering — is sound.

### Two developments touching decided work

**MCP Tasks** (extension, opt-in, host support varies) standardizes what
`compile-plan`/`compile-status`/`compile-cancel` were hand-built to do: durable
`taskId`, `tasks/get` with a server-suggested poll interval, `tasks/cancel`, TTL.

```
  SNP _TASK_STATES   not_started running stalled staged complete failed cancelled
  MCP Tasks          working  input_required  completed  failed  cancelled
```

`input_required` is the standard home for the `confirm=true` mutation gate that
`cf9e093` built by hand. Does not reopen the skills decision — Tasks applies to
tools — but if compile ever returns to the surface, do not rebuild polling.

**Skills over MCP.** The tool-vs-skill boundary is being standardized now.
Working Group since 2026-04-16; **SEP-2640 (Skills Extension, Resources-based,
Extensions Track) is In Review**, co-led by Anthropic. A filesystem skill is the
portable choice either way. Build no bespoke skill-serving mechanism; do not wait
for it either.

### SARIF

C4's choice is correct and there is nothing to wait for. 2.2 remains in
development (open issues as of June 2026); 3.0 candidate issues opened April 2026
including AI-related features.

Two recommendations:

- **Name the version in the emitter** — emit `$schema` and `version: "2.1.0"`,
  and validate before writing. An unvalidated findings format is how
  `health_reports` fills with documents a consumer silently refuses.
- **Record the version as a column**, not only inside the `jsonb`, so a future
  migration is detectable by query rather than by a consumer breaking.

## Why it never self-heals

`_IndexedSignature.matches()` (`wiki_ingest.py:518`) short-circuits re-ingest on
four inputs: content hash, model, chunk policy, and `capability_fingerprint`.
The stored fingerprint is:

```json
{"python":"3.12","parser_revision":2,"schema_version":1,
 "extractors":{"tables":{"version":"0.11.10","available":true},
               "figures":{"version":"12.3.0","available":true}}}
```

Recomputed today it is **byte-identical**, so `matches()` returns `True` and the
document is reported `unchanged` on every cycle. **The seven figures are never
retried.**

And the fingerprint is not wrong. `scout/capabilities.py` states its contract:
it records *"what was **available**, never what was configured"*, precisely to
stop a parser that could not look from claiming `figures_status: "ok"` (T5.1).
The figures extractor **was** available and did its job. What failed was the
remote *describer*, which is neither an extractor nor part of the environment
the fingerprint captures.

**The gap: a transient failure of a remote service is invisible to the
short-circuit that decides whether to try again.**

### CORRECTION 2026-09-21 — this section's mechanism is wrong

The reasoning above is sound about `matches()` and wrong about which documents
it governs. `_INDEXED_SIGNATURE_SQL` filters `c.metadata->>'corpus' = 'wiki'`.
The PDF is in the raw tier and carries no corpus stamp, so the short-circuit
never evaluates it at all. Measured on the live index, 2026-09-21:

```text
         corpus         | with_figure_state | with_content_hash
------------------------+-------------------+-------------------
 wiki                   |                 0 |              1963
 (raw: no corpus stamp) |               135 |                 0
```

The two states are in disjoint tiers: the tier that short-circuits has no
remote extraction that can fail, and the tier whose extraction can fail has no
short-circuit — `ingest_directory` re-parses every file on every run. So
**D-b's "never retried" is caused by nothing re-running the raw tier** (it is
not in `sync-job`'s cycle), not by a stale-signature skip.

What survives from this section: the fingerprint is not the place to record a
remote failure, for the reason given. What does not survive: `C-3.4`, "the
staleness short-circuit can see a failed remote extraction" — there is no
reachable input for which that gate could differ. Held for an owner scope
decision rather than implemented as an unreachable branch.

**Owner decision, 2026-09-21: build raw-tier failure visibility instead.** The
reachable defect is not a skip. It is that the failure is silent end to end:
the parser logs it, returns a smaller document, `ingest_document` writes that
document, and the run reports `ingested_ok` — because the write did succeed.
Nothing in the index could then answer "which documents did not arrive whole?".

Delivered: migration `008_document_extraction_status.sql` adds
`rag_documents.extraction_status`, an **outcome**, deliberately separate from
`capability_fingerprint`, which stays a record of what the environment could do
(the T5.1 reason above still holds). `ingest_document` writes it and returns it;
`snpmemory verify-extraction` (also stage `extraction` of the grouped `verify`
tool, and of `check`) names the documents; `engine_acceptance --group
ingest-integrity` names them too rather than counting degraded chunks. A
document with no recorded outcome reads as **unknown**, never as healthy —
which is the T5.1 shape one layer up, and is gated by
`extraction_visible.py --control`.

Verified end to end against a real PostgreSQL with the full migration ladder
applied, not against doubles, and controlled failing with the outcome unwritten.

## Finding 2026-09-21 — `compile-status` exits 0 for a handle that names no batch

Measured while wrapping the command as a skill script:

```text
$ snpmemory compile-status a-handle-that-names-no-batch -o json ; echo $?
{"completed": [], "detail": "no plan at /…/a-handle-that-names-no-batch",
 "done": 0, "pending": [], "started_at": null, …}
0
```

`docs/CLI_SPEC.md` gives this command exit `1` for "stalled / not started /
failed / cancelled". A handle that resolves to no plan at all returns **0** with
an empty progress report, so a caller reading the exit code — which is what a
script or an agent does — cannot tell a typo'd handle from an idle batch.

Not repaired here: changing a shipped command's exit code is a contract change
beyond `leaf-4.1`, and `compile-status` is consumed by the MCP tool surface as
well as the CLI. The skill wrapper compensates in the meantime: it requests
`-o json`, inspects `detail`, and emits a named `batch-exists` check so its
receipt reports `ok: false` for a handle that names nothing. `leaf-4.1:G3`
asserts that behaviour, so it cannot silently regress.

**Resolved 2026-09-24, owner decision: both halves.**

*The vocabulary,* which was the larger defect. `TaskState` had no word for "this
handle does not give me a batch", so `status_for` returned `NOT_STARTED` both
for a plan that does not exist and for a plan that cannot be parsed — the same
conflation `compile_plan` already names for the opposite case. `TaskState.UNKNOWN`
now covers both, and `detail` distinguishes them. The JSON payload is therefore
honest even to a caller that ignores exit codes entirely.

*The exit code.* `compile-status` now raises `input_error` for an unresolvable
handle, exactly as `compile-cancel` always has, giving exit `3` with a
machine-readable `kind: "input_validation"` envelope. CLI_SPEC §3 records it.
This is consistent with §1, which already assigns an unresolvable identifier —
"an unknown department" — to input validation, and with external practice:
`clig.dev` is silent on the case, while every comparable tool (`systemctl
status`, `kubectl get`, `docker inspect`) agrees only that it must not be `0`.

A real not-yet-started batch is unaffected: it still reports `not_started` with
its article count at exit `1`, the finding it always was. A control test pins
that, because a refusal that fired for every batch would be worse than the bug.

Under `mcp_result.py` the consequence is deliberate: exit `1` stays a *finding*
the agent reads and reasons about, while exit `3` becomes a tool error naming
`input_validation` — which is the truth an agent can act on, since the handle is
its own input. That matches MCP's guidance that execution problems stay visible
to the model rather than becoming protocol errors.

## Live finding 2026-09-21 — a publish race stops the vault watcher for good

`sync-job` read `unhealthy` with its vault watcher stopped:

```text
[sync-job] FATAL: /vault-replica: cold-start sync failed: vault unreadable:
  [Errno 2] No such file or directory:
  '/vault-replica/snapshots/70d34868.../wiki/V3-PROP-5d7bdd9f....md'
[sync-job] /vault-replica: stopped permanently; other corpora continue and
  this service will read unhealthy
```

The named file is the **propagation gate's own probe page**. `host-sync`
publishes by materialising `snapshots/<commit>/` and retargeting `current`, so
a walk can race a swap, and a page can be deleted while the cycle that listed
it is still reading. `WikiIndexer.index()` caught the resulting
`FileNotFoundError` alongside a genuinely absent vault and returned
`retryable=False`, so the watcher stopped permanently for an event the next
cycle would have absorbed. Recovery required a human restarting the container.

This is the same shape as D-c: a transient dependency failure treated as
permanent. It is also why `vault-change-propagates` was intermittent — the gate
that pushes and deletes a probe page is itself the most reliable way to trigger
the race it then fails on.

Fixed in source 2026-09-21: the handler now separates the two faults. A vault
whose **root** is absent or unreadable stays permanent (waiting cannot fix a
configuration fault); a file that vanished inside a still-readable tree is
`retryable=True` with status `vault changed under the walk`. The root check runs
through `asyncio.to_thread`, so it does not block the loop.

While fixing it, `test_wiki_indexer_reports_a_config_fault_as_permanent` turned
out to be asserting nothing: it passed `tmp_path`, which **exists**, so it
demanded "permanent" for a vault that was present and would have passed
whatever the classification did with a readable tree. It now points at a
genuinely absent directory, and a second test covers the vanished-page case.

**Not yet live.** The running images predate this fix, so the race can still
stop the watcher until `scout`/`sync-job` are rebuilt.

# Part VII — a false pass inside my own control (found 2026-09-17)

Found while integrating node-1. `leaf-1.2:G3` had been recorded as met; on
re-verification its control failed **1 run in 6**, and a tighter loop let the
plant escape **16 of 20**.

## The defect

`governance_control.py` plant C exposed `init` to prove the effect-derived rule
works independently of the never-expose list. But `init` **declares `--confirm`**,
and the rule is *"a write command may be exposed only behind --confirm"* — so the
gate is correct to permit it. Plant C could never be caught legitimately.

It reported "caught" because of **stale bytecode**. Plants B (`propose`) and C
were both `HIDDEN -> TOOL`, so the two planted files had identical byte size.
Python reuses a `.pyc` whose recorded source size and mtime match; when plant C
landed close enough to B's compile, the gate loaded B's bytecode, caught
`propose`, and the control credited that catch to C. Confirmed by running plant C
with bytecode disabled: `rc=0 NO WRITE CAPABILITY VERIFIED`, three times of three.

**`leaf-1.2:G3`'s earlier evidence was therefore a false pass for plant C.**
Plants A and B were sound.

## Fix

- Plant C now exposes `up` (`write`, no `--confirm`, not on the never-expose list).
- Plant D added: `down` (`destructive`, *with* `--confirm`) must still be caught —
  confirmation never licenses a destructive tool.
- Both plants are validated against their command's own declaration before use,
  so a plant cannot silently become invalid again.
- C and D must be caught **by name** in the gate's output, not by any failure.
- Every gate run starts with `scout/cli/__pycache__` removed and bytecode off.
- Result: 8 of 8 runs stable.

## Blast radius, measured

- The audit mutation sweep (Part III) had **zero** same-module mutants of
  identical byte size, so none of its 58 verdicts could have been masked this
  way. Both mutation harnesses now run children with bytecode off regardless.

## An open policy question this surfaced — for the owner

Under the derived rule, `write` commands that declare `--confirm` may be exposed
as tools without the governance gate objecting. Beyond `propose` and `ingest`
(protected by name), that includes **`init`, which generates and rotates
credentials**, plus `install-agent`, `mcp-config` and `compile`. The gate's stated
scope is *"no served tool performs git push or vault write"*; credential rotation
is outside that scope, so the gate is consistent with its title. Whether `init`
belongs on the never-expose list is a policy decision, not recorded here as a
defect.
