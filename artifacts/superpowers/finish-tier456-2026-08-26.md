## The finding that reorganised the work

The bibliography was **21% of the parsed text and 18% of the indexed chunks** —
23 of 127 — and reference entries are dense with exact paper titles, so a query
that *is* a paper title ranked the bibliography above the section discussing it.

**It was also T4.2's raw material.** The same 87 entries the citation graph
needed were the noise polluting retrieval. Extracting them once served both:

| | Before | After |
| --- | --- | --- |
| Parsed text | 109,457 chars | 92,008 |
| `[CrossRef]`-bearing chunks | 23 | 2 (both false positives) |
| References in metadata | 0 | 87 |
| Pages with correct prose at rank 1 | **3 of 5** | **4 of 5** |

Entry 50 — `Hinton, G.E. Deep belief networks. Scholarpedia 2009` — is *exactly*
the fragment that ranked first for "Convolutional Neural Networks" in the status
check. The noise and the graph material were the same bytes.

**No reranker was added**, and that decision rests on the measurement rather than
the literature. The one page that did not improve has a hint that **is the
paper's own title**, so the paper's `Citation:` block is the best match in the
document — retrieval is correct and the hint is wrong. A cross-encoder would not
change that. Recorded with per-page numbers and a revisit trigger in
`artifacts/superpowers/retrieval-baseline-2026-08-25.md`.

## Review pass

### Blocker
None.

### Major
None outstanding. Three were found and closed during execution:

1. **`snpmemory ingest` cannot run from the host without exporting `.env`.**
   `postgres_settings()` reads ambient `os.environ` while the CLI resolves
   `.env` into its own `Config` — the same class as the Tier 1 `fetch` defect, in
   a different place. Worked around for the re-index; **recorded, not fixed.**
2. **The corpus now depends on where ingestion runs.** The host has
   `pdfplumber`; the containers do not. The host re-index produced 3 table
   sections the container cannot, and `sync-job` will drop them on its next
   re-index. This is SH-6 in a new form — the *same* parser drifting from itself.
   **Recorded, not fixed.**
3. **T4.1's count was wrong.** 12 articles remain, not 10: only 3 of the 5
   compiled pages correspond to current headings.

### Minor

1. **`ruff format` landed at the wrong moment** — see the honest note below.
2. **The reference parser is regex-shaped and has seen one publisher's style.**
   87/87 here; a second document with different conventions is an untested case.
   It reports what it cannot parse (18 titles) rather than guessing, which is the
   mitigation, not a fix.
3. **`Works Cited` only appears on pages compiled from now on.** The 5 existing
   pages predate it. That inconsistency is deliberate — recompiling them to match
   would double the cost for a cosmetic gain — but it is an inconsistency.
4. **`_lift_references` runs on every parse**, including the many test parses.
   It costs a full-text regex scan per document. Negligible at one document.
5. **The NO_EVIDENCE probe assumes a path-filtered retrieval returns nearest
   neighbours regardless of query.** True of pgvector's vector arm, not
   guaranteed by the `RagBackend` protocol. Documented at the call site.

### Nit

1. `MAX_CITATION_RANGE = 30` is a judgement, not a measurement.
2. `looks_like_reference_page`'s "a quarter of lines start with `N.`" threshold
   is likewise tuned to one document.
3. The two remaining `[CrossRef]`-matching chunks are false positives of the
   *detector* used to measure, not of the parser. Harmless, but the measurement
   command overstates by 2.
