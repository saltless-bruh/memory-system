# Plan — Tier 1: complete the CLI surface

**Date:** 2026-08-24 · **Branch:** `fix/architecture-security-hardening` (HEAD `2d2b9dd` + Tier 0 work)
**Scope:** `docs/REMAINING_TASKS.md` Tier 1 — T1.1, and the 14 commands `docs/CLI_SPEC.md`
specifies but does not implement. Nothing from Tier 2+.

---

## What the 2026 research changed

Searched before planning, as asked. The repository's CLI design already matches
the current consensus closely — arguably exceeds it: seven exit codes where the
common agent-CLI guidance uses four, a machine-stable `ErrorKind`, an `hint`
field for remediation, absolute stdout/stderr discipline, and lazy config
resolution so `schema` answers with no credentials. Three things came out of the
search that are worth acting on, and one that is worth *not* acting on.

### F-1 — `snpmemory schema` does not conform to the spec this repo says it follows (BLOCKING for the rest)

`docs/CLI_SPEC.md` states it follows [The CLI Spec](https://clispec.dev/). I
fetched the actual schema (`https://clispec.dev/schema/v0.3.json`, v0.3
candidate, August 2026) and compared. Its required top-level fields are:

```
["clispec", "name", "version", "commands", "errors"]
```

`snpmemory schema -o json` emits **`{"commands": [...]}`** and nothing else. Four
of the five required fields are absent. Per-command, the spec requires
`["name", "description", "effects"]` and the emitted records carry `name`,
`summary`, `prerequisite`, `effect`, `outcomes`, `errors` — so `description` is
named `summary`, and `effect` uses a different taxonomy (`read`/`write`/
`destructive`) from the spec's (`read_only`/`idempotent`/`non_idempotent`).

Most consequentially: **no command declares its arguments.** `args` is absent
everywhere. The spec's own principle is *"Agents should never need to parse
`--help`"*, and `CLI_SPEC.md` §4 repeats it verbatim — but today an agent that
reads `schema` learns that `compile-plan` exists and cannot learn that it needs
`--confirm`. It has to parse `--help` after all.

This is why the plan fixes the declaration shape **before** adding commands.
Retrofitting 14 more records is 14× the work and, per the stability rule below,
schema output an agent has started reading is itself a contract.

### F-2 — the text default is legitimate, and the spec says how to declare it

Current agent-CLI guidance is that structured output should be the default when
stdout is not a TTY. `OutputFormat.AUTO` here resolves to `text` when piped, on
purpose, because existing CI steps and agent workflows read that text.

The spec permits this exactly once: *"Structured output SHOULD be the default
when piped; a tool that keeps a human-readable default MAY do so **if it
declares that default in the top-level `output` field**."* So the divergence
stays — and becomes conformant by declaring `output: {tty: "text", piped:
"text"}`. Changing `AUTO` instead would violate the stronger rule that a
CLI agents already use is a stable contract.

### F-3 — the confirmation pattern is richer than exit 5 alone

Current guidance: a mutation without `--confirm` should return not just the
refusal code but *"a JSON envelope describing proposed changes plus an exact
re-run command"*, and deliberately not an interactive prompt. `compile-plan`
already refuses correctly (exit 5). Every mutating command added here adopts the
fuller shape: what would change, and the literal command that would do it.

### F-4 — cyclopts is current

Installed 4.22.4; latest is 4.22.x (Jul 2026). No migration needed, and the
`--help` defect is ours, not the framework's (see step 1).

### Goal

Every command in `docs/CLI_SPEC.md` exists, behaves as specified, and is
discoverable from `snpmemory schema` without reading `--help`. Concretely:

1. `snpmemory --help` and a bare `snpmemory` exit `0`, not `2`.
2. `snpmemory schema` emits a document that validates against
   `clispec.dev/schema/v0.3.json`, including each command's arguments.
3. Twelve of the fourteen missing commands are implemented, tested, and carry an
   MCP exposure decision. Two are blocked on other tiers and are stated as such
   rather than half-built.

Non-goals: changing any existing command's behaviour, output, or exit codes;
touching the MCP server's tool set beyond the mandatory policy entries; anything
in Tier 2+.

### Assumptions

- **A1.** `docs/CLI_SPEC.md` is the binding contract for names and flags. Where
  this plan and the spec disagree, the spec wins or the spec changes first — an
  agent-facing name is a contract, and renaming later is the failure mode the
  stability rule exists to prevent.
- **A2.** No new backend is needed for the read-only wave. `scout/diy_engine.py`
  is a complete in-repo wiki search engine over the same vault, and
  `scout/vault.py` loads and parses pages. `search` and `read` build on those;
  `fetch` builds on `scout/core.py::rag_fetch`. **Verified by inspection, not
  assumed** — but if `search` turns out to need the running basic-memory server,
  step 9 changes shape and nothing else does.
- **A3.** Every backing script exists: `mint.py`, `compile_note.py`,
  `propose_page.py`, `ingest_v2.py`, `ci_address_gate.py`, `bootstrap_secrets.py`,
  `export_mcp_config.py`, and `scout/healer.py`. These commands are wrappers with
  an exit-code contract, not reimplementations.
- **A4.** Two commands are genuinely blocked and are **not** in scope:
  `extract` needs the `derived/` asset store (T4.3, deferred pending your
  discussion), and `install-agent` needs the agent package to stop being a
  25-file subset (Tier 3). Building either now would ship a command that works
  on nothing.
- **A5.** The `mcp_policy.undecided_commands()` guard fails the suite for any
  command with no exposure decision. That is the mechanism that keeps this plan
  honest, and every command step relies on it.

## Plan

### Phase A — the contract surface (do this before adding commands)

**1. `snpmemory --help` and bare `snpmemory` exit 0**
   - Files: `scout/cli/app.py`, `tests/test_cli_core.py`
   - Change:
     - cyclopts prints help and returns `None` (verified: `app(['--help'], …)`
       returns `NoneType`). `main()` treats any non-`CommandResult` as a
       programming error, so it prints *"command did not return a
       CommandResult / this is a bug in snpmemory"* and exits `2` — the
       infrastructure code, on a healthy binary.
     - Treat `None` as "cyclopts handled it and printed" → exit `0`. Keep the
       bug envelope for a non-`None` non-`CommandResult`, which really is a
       programming error.
   - Verify:
     - `snpmemory --help; echo $?` → `0`, and the banner is absent.
     - `snpmemory; echo $?` → `0`. `snpmemory verify-vault --help; echo $?` → `0`.
     - `snpmemory bogus-command; echo $?` → still `3` (input validation).
     - New regression tests for each of those four.

**2. Vendor the spec schema and add a failing conformance test (TDD, red)**
   - Files: `tests/fixtures/clispec-v0.3.json` (new), `tests/test_cli_schema_conformance.py` (new)
   - Change:
     - Vendor `https://clispec.dev/schema/v0.3.json` (32 KB) rather than fetching
       at test time: a test that reaches the network fails in CI for reasons
       unrelated to the code, and pins nothing.
     - Validate `snpmemory schema -o json` against it.
   - Verify: `pytest tests/test_cli_schema_conformance.py` — **fails**, naming the
     missing `clispec`, `name`, `version`, `errors`. Do not proceed until it fails
     for that reason.
   - Note: `jsonschema` is a new test-only dependency. If that is unwelcome,
     assert the required keys directly and keep the vendored file as the
     reference — say so and the step shrinks.

**3. Extend `CommandSpec` with the fields the spec requires**
   - Files: `scout/cli/registry.py`, `tests/test_cli_registry.py`
   - Change:
     - Add `args: tuple[ArgSpec, ...]`, `cardinality`, `output_kind`,
       `confirmation_bypass_arg`, `requires_tty`, `stability`, `example`.
     - `ArgSpec(name, type, short=None, required=False, default=None, enum=(), description="")`
       — the spec's own required pair is `["name", "type"]`.
     - Map `Effect` onto the spec's `effects` taxonomy at serialisation time
       (`READ → read_only`, `WRITE → idempotent`, `DESTRUCTIVE → non_idempotent`)
       rather than renaming the internal enum, so no existing consumer breaks.
   - Verify: `pytest tests/test_cli_registry.py`; `mypy scout scripts` clean.

**4. Emit a conformant document (green)**
   - Files: `scout/cli/commands/schema.py`, `scout/cli/declarations.py`
   - Change:
     - Top level: `clispec` (version), `name`, `version` (package version),
       `description`, `output: {tty: "text", piped: "text"}` (F-2 — this is what
       makes the text default conformant rather than a silent divergence),
       `global_args` (`--output`/`-o`, `--no-color`), `commands`, `errors`.
     - Backfill `args` for the ten existing commands from their real signatures.
       `compile-plan` gets `confirmation_bypass_arg: "confirm"`.
   - Verify:
     - Step 2's test passes.
     - `snpmemory schema -o json | jq '.commands[] | select(.name=="compile-plan") | .args'`
       lists `--confirm`, `--background`, `--dry-run`, `--no-resume`, `--allow-uncertain`.
     - Full suite green; every pre-existing schema test still passes.

**5. `snpmemory schema <command>` narrowing**
   - Files: `scout/cli/commands/schema.py`, `tests/test_cli_schema_conformance.py`
   - Change: optional positional argument narrowing the document to one command

   - Verify: `snpmemory schema verify-vault -o json | jq '.commands | length'` → `1`;
     `snpmemory schema nope; echo $?` → `3`.

**6. Update `docs/CLI_SPEC.md` to record conformance**

### Risks & mitigations

- **R1 — Twelve commands is a large surface to add at once.** Mitigation: the
  waves are independently shippable and ordered by risk, read-only first. Stop
  after any wave and the tool is coherent; that is the point of the ordering.
- **R2 — A wrapper that quietly reimplements its script.** The real risk of
  "expose script X as command Y" is a second copy that drifts. Mitigation: every
  command imports and calls the existing module; a step that finds itself copying
  logic stops and extracts a shared function instead.
- **R3 — Widening the write surface widens the blast radius.** `compile`,
  `propose`, `heal`, `ingest`, `init` all mutate. Mitigation: F-3's confirmation
  envelope on each; `--dry-run` where the backing script has one; and the
  existing rule that codes ≥ 2 never mutate, which `NON_MUTATING_CODES` already
  encodes.
- **R4 — `fetch` is the one command that can leak across a security boundary.**
  A `--dept` bug hands a caller another department's evidence. Mitigation: the
  narrowing-only test in step 9, plus the explicit "ACL `all` is not caller
  authority" assertion. If that test cannot be written cleanly, stop and fix the
  seam before shipping the command.
- **R5 — Schema output is itself a contract once agents read it.** Phase A
  changes its shape. Mitigation: do it now, before 14 more commands and before
  wider adoption; the additions are new keys, and `summary` can remain alongside
  `description` for one release if anything already reads it.
- **R6 — `jsonschema` as a new test dependency** (step 2). Mitigation: the
  fallback is stated in the step — assert required keys directly and keep the
  vendored schema as documentation.

### Rollback plan

Phase A and each wave are separate commits, and nothing later depends on an
earlier wave's *code*:

- Step 1 is a few lines in `main()`; `git revert` restores today's behaviour
  (which is the bug, so this is a last resort).
- Phase A (steps 2–6) is additive: new keys in a document, new optional fields on
  `CommandSpec`. Reverting restores the old schema output; no command stops
  working.
- Each command in Phase B is its own commit touching one command module, one
  declaration, one policy entry, one test file. Reverting one removes exactly one
  command — and `mcp_policy`'s guard will fail loudly if a declaration is removed
  without its policy entry, which is the intended tripwire.
- No migration, no data change, no schema change in PostgreSQL. Nothing here
  touches the corpus.

1. **`jsonschema` as a test-only dependency** (step 2) — or assert the required
   keys by hand? Recommended: add it. Hand-rolled validation of a 32 KB schema
