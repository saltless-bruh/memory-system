## What was built

- **`invoke.py`** — one path from a declared command to a `CommandResult`, shared by the
  CLI and MCP, so the two surfaces cannot answer differently for the same command.
- **`mcp_policy.py`** — the exposure decision per command, with a test that **fails the
  suite** when a new command has none. Nine commands collapse to four tools, because
  tool-list bloat measurably degrades tool selection.
- **`mcp_result.py`** — exit 1 is a *successful* tool call carrying a finding the agent
  must reason about; exits 2–7 are tool *errors*. Exit 2 never appears as a result,
  because `ci_address_gate.py`'s contract is that infrastructure failure never authorises
  mutation.
- **`local_server.py`** — annotations derived from each command's declared `Effect`, so a
  command cannot acquire write authority without that showing up in the registry, in
  review.
- **`tasks.py`** — progress computed from the plan file and staging directory. No second
  store was built: Step 3's checkpointing already *is* a durable per-article record.

## Review pass

**Blocker** — none outstanding. One was found and fixed during execution (below).

**Major — `compile_status` cannot see a batch started by a different checkout.** The handle
is a relative plan path resolved against the current working directory. Two agents in two
clones would each report on their own vault. Correct for a local tool; worth stating if
this is ever packaged for wider use.

**Minor — the detached background run is not supervised.** `--background` starts the
process and returns. If it dies between staging two articles, `compile-status` correctly
reports `stalled`, but nothing restarts it; a human or agent must re-run to resume.
Deliberate — automatic retry against a rate-limited free tier is how quota gets burned.

**Minor — `compile_status` reads the vault with `rglob` per slug.** Fine for tens of
pages, linear in vault size for thousands.

**Nit** — `plan_articles` writes with `out=` outside the repo if given an absolute path.
The command is LOCAL and the user already has filesystem authority, so this is not a
boundary crossing, but it is unguarded.

## Defects found during execution — all four were mine

1. **BLOCKER, shipped in `dea240c`: every multi-word CLI flag was broken.** `--dry-run`,
   `--max-depth`, `--skip-groundedness`, `--no-resume`, `--allow-uncertain`. Registering
   commands through a generic `(*args, **kwargs)` wrapper left cyclopts no signature to
   parse from, and it did not degrade gracefully — `--dry-run` demanded a value and
   `--max-depth 1` arrived as a keyword literally named `max-depth`. Fixed by loading the
   implementation at registration, which is safe only because every command module keeps
   its heavy imports inside its functions — now enforced by a subprocess test that fails
   if loading a command adds any environment variable.
2. **The registry was populated only as an import side effect of `app.py`.** Any consumer
   that did not import the dispatcher saw zero commands. `ruff --fix` twice deleted that
   import as "unused", once emptying the entire command surface. Declarations moved to
   their own module exporting a concrete `DECLARED` tuple. Test pollution had been masking
   it: `test_mcp_policy` imported declarations, populating the global registry for every
   other test.
3. **A `CliError` escaped raw at the MCP boundary**, so a routine refusal reached the
   client as an unhandled exception with a traceback attached.
4. **`compile_status` reported `complete: 0/3`** because `done` counted staged files and a
   successful publish deletes staging.

Defects 3 and 4 were only visible by driving a real client. Neither the unit tests nor the
CLI would have shown them.
