---

## What the 2026 research changed

### F-1 — Tasks are no longer something to hand-roll (and both pinned SDKs already implement them)

The repo built its own long-running-job protocol: `compile_plan --background`
returns a handle, `compile_status` polls it, `.run.json` carries the pid, a dead
pid reads as `stalled`. That is the MCP **Tasks** design, written by hand before
it was available.

It is available now:

```
mcp 1.29.0      → CreateTaskResult, GetTaskRequest, CancelTaskRequest, Task(taskId, status, ttl, pollInterval)
fastmcp 3.3.1   → fastmcp.server.tasks: TaskConfig(mode='forbidden'|'optional'|'required', poll_interval=5s)
```

Opting a tool in is a `TaskConfig` on the decorator, not a rewrite. A
task-capable client then gets `tasks/get` polling, `tasks/cancel`, and a taskId
that survives a disconnect, all handled by the framework.

**But there is a version fork worth stating before anyone builds on it.** Tasks
shipped as an *experimental core feature* in **2025-11-25** and were moved to an
**extension** (`io.modelcontextprotocol/tasks`) in the current **2026-07-28**
spec. The pinned SDK reports `LATEST_PROTOCOL_VERSION = 2025-11-25`, and its
`Task` model carries `ttl` / `pollInterval` — the core-experimental field names,
not the extension's `ttlMs` / `pollIntervalMs`. So adopting Tasks today means
adopting the shape this SDK speaks and letting fastmcp carry the migration when
it moves.

**Decision this plan takes:** adopt `TaskConfig` for `compile_plan` as an
*additive* surface, and keep the plan-path handle as the durable record.
Rationale: an MCP taskId lives with the server process, while the staging
directory and `.run.json` survive a server restart, a machine reboot, and a
client that has never heard of Tasks. Replacing the durable record with the
session one would be a downgrade dressed as modernisation.

### F-2 — Four Tasks rules apply whatever the wire format, and three are currently unmet

From the extension's normative text:

| Rule | Status here |
| --- | --- |
| "The task must be **durably created before** sending the response" | **Met.** The staging directory and `.run.json` are written before the handle is returned. |
| Terminal statuses are `completed` / `failed` / `cancelled` | **Unmet.** `TaskState` has no `FAILED` and no `CANCELLED`. A crashed batch reads `stalled` forever and a cancelled one has nowhere to go. |
| A task carries a **TTL** and a suggested **poll interval** | **Unmet.** Nothing tells a caller how often to poll or when a handle has gone stale — which is also T2.3's stale-staging problem in another guise. |
| "Cancellation is cooperative — the server acknowledges the intent but is not obligated to stop" | **Unmet.** There is no way to cancel a background compile at all. It runs until it finishes or the machine stops. |
| "**Never return a task to a client that did not declare support**" | N/A until step 8, then enforced by fastmcp. |

Fixing the three unmet ones is Tier 2's real content. They are the same gaps
T2.3 and T2.4 name, arrived at from the protocol's side.

### F-3 — The working directory belongs in the exported config

Current guidance for stdio client configs: the leading entries of `args` are
conventionally used to pin where the command runs, "telling the tool to treat a
directory as the working context." That is exactly **T2.2**: `status_for` derives
the staging directory from a relative plan path, so a client that launches
`snpmemory mcp` from its own cwd reports `not_started` for a batch that is
running. Pinning the root in the exported config *and* in the server closes it
from both ends.

### F-4 — Nothing else in the transport story changed

stdio and Streamable HTTP remain the two standard transports; stdio is still
"the client starts the server as a child process and talks over its stdin and
stdout." No migration is implied for `snpmemory mcp`.

### Goal

An agent installed from this repository can find the authoring tools, drive a
long batch without holding a connection open, see honestly whether that batch is
still alive, and stop it. Concretely:

1. `mcp-config` exists as a command and emits **three** servers, including the
   local stdio one, with a pinned working directory.
2. A handle means the same thing from any directory.
3. A batch that fails, stalls, or is cancelled says so, and a resumed run cannot
   silently reuse pages generated from a plan that has since been edited.
4. `compile_plan` is task-capable for clients that support it, without the
   plan-path handle losing its meaning for everything else.

Non-goals: migrating to the 2026-07-28 extension wire shape (fastmcp's job);
adding tools to the MCP surface beyond what exists; anything in Tier 3+.

### Assumptions

- **A1.** `fastmcp==3.3.1`'s `TaskConfig` produces the 2025-11-25 core-experimental
  shape, since `mcp.types.Task` carries `ttl`/`pollInterval`. **Step 8 verifies
  this against a real `fastmcp.Client` before anything depends on it** — if the
  handshake does not negotiate, step 8 stops and the rest of the plan is
  unaffected, because it is deliberately last.
- **A2.** The plan-path handle stays the durable record. An MCP taskId is scoped
  to the server process; the staging directory is not.
- **A3.** `scripts/export_mcp_config.py` and `packages/snp-agent/manifest.json`
  are the only two places a client learns which servers exist. Verified by
  inspection; step 3 adds a test so it stays true.
- **A4.** `snpmemory` is on PATH after install (`[project.scripts]` declares it),
  so the exported stdio entry can name the command rather than a path into a
  checkout the user may not have.
- **A5.** Cancellation can be cooperative and still be useful: writing a
  cancellation marker that the batch checks between articles stops it at an
  article boundary, which is where the staging directory is already consistent.

### Phase D — T2.3 / T2.4: honest states, staleness, and a way to stop

**7. Plan-hash guard, TTL, poll interval, and the two missing terminal states**
   - Files: `scout/cli/tasks.py`, `scripts/compile_plan.py`, `tests/test_tasks.py`,
     `tests/test_compile_plan.py`
   - Change:
     - Write the plan's content hash into `.run.json` at start. A resume whose
       plan hash differs **refuses** rather than reusing pages generated from the
       old plan. (Today it silently reuses them and reports success.)
     - Add `FAILED` and `CANCELLED` to `TaskState`; a run that exits non-zero
       records why, so a dead batch stops reading as `stalled` forever.
     - Carry `poll_interval` and a TTL in the status payload, so a caller is told
       how often to poll and when a handle is too old to trust.
   - Verify:
     - Edit the plan between two runs → the second refuses, names the mismatch,
       and reuses nothing.
     - A batch killed mid-run reports `failed` with its exit code, not `stalled`.
     - The existing resume test still passes and still spends zero model calls.

**8. Cooperative cancellation**

### Risks & mitigations

- **R1 — Tasks is the riskiest step and it is last on purpose.** Step 9 is the
  only one depending on an unverified assumption, and it verifies that assumption
  before changing anything. Everything of value in this plan lands whether or not
  step 9 does.
- **R2 — `mode="optional"` could still change what today's clients receive.** The
  mitigation is the existing MCP test suite: it must pass **unchanged**. If a
  non-task client's response shape moves at all, revert step 9.
- **R3 — A plan-hash guard could refuse a legitimate resume.** Whitespace or a
  reordering would trip it. Mitigation: hash the *parsed* article list, not the
  raw bytes, so a comment or a reflow does not invalidate a running batch; and the
  refusal names the difference rather than saying "mismatch".
- **R4 — Cancellation between articles can look unresponsive.** A long article
  keeps running after the request. Mitigation: say so — `compile-cancel` reports
  "will stop after the current article", and the state moves to `cancelled` only
  once it has actually stopped. Claiming otherwise would be the lie the whole
  status contract exists to avoid.
- **R5 — Pinning a server root could break a legitimate out-of-tree plan path.**
  Mitigation: the root is the repo the server was launched in, which is where
  every plan lives today; the refusal names the root, and the escape check is
  what bounds a tool call's write surface.
- **R6 — Three config surfaces (exporter, manifest, docs) can still drift.**
  Mitigation: steps 3–4 add tests asserting the exporter and manifest agree, and
  that the exporter agrees with `mcp --list-tools`. Documentation is the one
  surface a test cannot hold; it is checked by hand in step 5.

### Rollback plan

Every phase is a separate commit and nothing later depends on an earlier one's
code:

- Phase A is additive: a new test file and a new command. Reverting removes the
  command; nothing else changes.
- Step 3–4 add a third entry to two config files. `git revert` restores the
  two-server config exactly; no client breaks, they simply stop seeing the local
  server again.
- Step 6 changes path resolution. The pinned before-test makes the regression
  obvious if reverted.
- Steps 7–8 add fields to `.run.json` and a marker file. Old markers without a
  plan hash must still be readable — a resume against one warns rather than
  refusing, so a run started before the upgrade is not stranded. That
  backward-compatibility case gets its own test.
- Step 9 is one decorator argument. Reverting it returns `compile_plan` to a
  plain tool.

No migration, no data change, nothing touching the corpus or the vault.

### Decisions needed

1. **Adopt `TaskConfig` now, on the SDK's 2025-11-25 shape (step 9)?**
   Recommended: yes, as `mode="optional"` and last in the plan. It is one
   decorator argument, fastmcp owns the wire format and its migration, and the
   durable handle is untouched either way. The alternative — waiting for fastmcp
   to ship the extension shape — costs nothing now but leaves `compile_plan`
   holding a connection open for minutes on task-capable clients.
2. **Should `compile-cancel` be an MCP tool, or CLI-only?** Recommended:
   CLI-only for now (`Exposure.HIDDEN`). The tool surface is deliberately four,
   and an agent that started a batch can stop caring about it; an operator is the
   one who needs to stop it. If step 9 lands, `tasks/cancel` gives task-capable
   clients cancellation natively anyway.

## Amendments during execution

**AM-1 (step 1) — `ingest` resolved relative paths against the process cwd.**
Found while writing the boundary tests. `raw_root` was anchored to the checkout
but the `--path`/`--dir` argument was not, so `snpmemory ingest --dir raw/papers`
refused its own corpus from anywhere except the repository root, reporting
"outside the corpus root". Fail-safe (exit 3, nothing mutated) but wrong, and it
is T2.2's defect class in a second place. Fixed in `scout/cli/commands/ingest.py`
by anchoring a relative argument to `repo`; regression test added. Step 1's scope
grows by one two-line fix and one test.

**Decisions, taken as recommended.** (1) `TaskConfig` is adopted on the SDK's
2025-11-25 shape, `mode="optional"`, last in the plan. (2) `compile-cancel` is
CLI-only with `Exposure.HIDDEN`.
