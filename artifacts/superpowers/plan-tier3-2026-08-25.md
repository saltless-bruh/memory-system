## What the 2026 research changed

### F-1 — There is now a standard for exactly what `manifest.json` hand-rolls

**Agent Plugins 1.0.0**, published **2026-08-06**, is a vendor-neutral format for
packaging Agent Skills *and* MCP servers as one distributable folder. Core
maintainers include Amazon, Cursor, Microsoft, OpenAI, Vercel and Google. The
shape:

```
plugin-root/
├── plugin.json          # required: $schema + name, closed schema
├── mcp.json             # optional: typed MCP server declarations
├── skills/<name>/SKILL.md
└── com.example.client/  # client-specific, reverse-domain namespace
```

`packages/snp-agent/manifest.json` fails this on nearly every axis, and the
mismatches are not cosmetic:

| Spec rule | What we have |
| --- | --- |
| `$schema` + `name` required; schema is **closed** (`additionalProperties: false`) | no `$schema`; `mcpServers`, `entrypoints`, `rbac`, `compatibility`, `engines`, `displayName` are all unknown top-level fields |
| "MCP servers are declared in a separate `mcp.json`… **never inline in the manifest**" | declared inline in `manifest.json` |
| each server entry needs a closed `type`: `stdio` \| `streamable-http` \| `sse` | our entries use a free-text `transport` key |
| non-standard data goes in `extensions`, keyed by reverse-domain | `rbac` and `entrypoints` sit at top level |

Adopting it is cheap — `plugin.json` is metadata, and `install-agent.sh` copies
files regardless of any client implementing the spec — and it converts a bespoke
manifest that only our own two tests understand into one a conformant client can
load.

**One thing the standard does *not* solve, and the plan must not pretend it
does.** Agent Plugins defines `${PLUGIN_ROOT}` / `${PLUGIN_DATA}` expansion for
stdio servers, which looks like the answer to Tier 2's `--root` pinning. It is
not: `PLUGIN_ROOT` is the *installed plugin's* directory, the spec requires every
resolved path to stay **within** it, and the checkout `snpmemory mcp` must serve
is outside it by construction. A portable plugin therefore cannot pin the
checkout. The honest options are an `env` value the installer or user fills, or
leaving the local server to `snpmemory mcp-config`, which already writes it
correctly from the checkout.

### F-2 — The Agent Skills spec is explicit, and T3.1 is bigger and smaller than recorded

Normative frontmatter: `name` (1–64 chars, lowercase alphanumeric and hyphens,
no leading/trailing/consecutive hyphens, **must match the parent directory**) and
`description` (1–1024 chars, must say *what* and *when*). Optional: `license`,
`compatibility`, `metadata`, `allowed-tools`. Every other key is ignored by
conformant runtimes. The spec adds a safety rule: **avoid `<` and `>` anywhere in
frontmatter**, because they can inject unintended instructions into the system
prompt.

Measured against the repository:

* **Bigger than recorded.** The 6 invalid frontmatters are not in
  `packages/snp-agent` at all — they are in `.agent/skills` **and**
  `.claude/skills`, which are byte-identical copies. So it is 12 files, not 6.
* **Smaller than recorded.** They are all one defect: an unquoted `description:`
  whose value contains `: ` (`"Systematic debugging: reproduce…"`). The repo
  already solved this for the 8 `snp-*` skills with a `>-` folded scalar.
* **A third thing, unrecorded.** That `>-` fix puts a `>` in the frontmatter of
  all 8 `snp-*` skills, and `superpowers-workflow` carries `->` arrows in its
  description. Both are exactly what the spec's safety rule names. One
  double-quoting pass fixes the invalid six *and* clears the angle brackets from
  all seventeen.
* Names, directories and description lengths are otherwise all valid.

### F-3 — There are **five** config surfaces, not three, and the fifth is the most drifted

Tier 2's risk R6 said three surfaces could drift (exporter, manifest, docs) and
step 4 found a fourth (`install-agent.sh`). There is a fifth:
`scripts/export_agent_bundle.py` hardcodes its own per-client MCP configs at
lines 160–210, and they disagree with everything else:

* names the wiki server **`basic-memory`** — the namespace T3.0 is about;
* uses **`SCOUT_AUTH_TOKEN`** inside `Authorization: Bearer ${…}`, while
  `docs/CONNECT_AGENTS.md`, `export_mcp_config.py` and `install-agent.sh` all use
  `SCOUT_AUTH_HEADER` (the *complete* header value). A user who follows the
  documentation and exports `SCOUT_AUTH_HEADER` gets a config from this exporter
  that cannot authenticate;
* emits no `snpmemory` server at all.

### F-4 — The 25-file gap is structurally unguarded

`tests/test_agent_package_sync.py` enforces `.agent` ↔ `.claude` parity across
four subtrees, and `packages/snp-agent` ↔ `.agent` for **root files only**. So
the package can lose any number of skills, workflows or instructions without a
test noticing — which is how 25 files went missing. Whatever is decided about
scope, it has to be decided *in a file a test reads*.

### F-5 — Validation tooling exists, but the repo already has a better pattern

`skills-ref` ships on PyPI, npm and crates.io with a `validate` subcommand. Its
own authors state it is "intended for demonstration purposes only and not meant
to be used in production", so it does not belong in this project's dependency
graph. The repository already established the right pattern in Tier 1: vendor
the schema (`tests/fixtures/clispec-v0.3.json`) and validate with `jsonschema`
in a test. Do the same with the two Agent Plugins schemas, and encode the Agent
Skills frontmatter rules directly — they are six rules, not a schema worth
importing a library for.

### Goal

The package a third party installs is a deliberate, standard-shaped, validated
subset of what this repository runs — and every surface that tells an agent how
to connect says the same thing. Concretely:

1. Every `SKILL.md` in the repository parses as strict YAML and conforms to the
   Agent Skills spec, enforced by a test.
2. `packages/snp-agent` is a valid Agent Plugins 1.0.0 plugin, validated against
   the vendored schemas.
3. The package's contents are what the manifest says they are — the 25-file gap
   is closed by a *decision* recorded in the manifest and enforced by a test,
   not by an accident.
4. No agent installed from this repository is told to call a tool that does not
   exist, and all five config surfaces agree.
5. `snpmemory install-agent` exists.

Non-goals: publishing to any marketplace; implementing an Agent Plugins *client*;
changing what the skills teach; anything in Tier 4+.

### Assumptions

- **A1.** Agent Plugins 1.0.0's schemas are fetchable and stable at the `$id`
  URLs quoted in F-1. Step 3 vendors them and pins the exact `$schema` constant,
  so a later spec revision is a visible test failure rather than silent drift.
- **A2.** No client this project targets *requires* Agent Plugins today.
  `install-agent.sh` remains the working install path throughout; the standard
  buys future portability, not present function. If that assumption is wrong in
  either direction, nothing else in the plan changes.
- **A3.** `.agent/` stays the authoritative contract and `.claude/` its mirror.
  The existing parity test says so, and this plan does not renegotiate it.
- **A4.** `manifest.json`'s `entrypoints` and `rbac` keys have exactly two
  consumers — `scripts/export_agent_bundle.py:42` and
  `tests/test_agent_package_sync.py:58`. Verified by grep; step 8 updates both.
- **A5.** A portable plugin cannot pin the SNP checkout (F-1). The local stdio
  server is therefore declared with an `env` value that is **empty by default**,
  and `snpmemory mcp` refuses clearly when it is unset rather than serving the
  wrong tree.

## Plan

### Phase A — fix what is wrong today, before deciding anything

**1. Make every `SKILL.md` frontmatter strict-YAML valid and angle-bracket free**
   - Files: `.agent/skills/*/SKILL.md`, `.claude/skills/*/SKILL.md` (17 each)
   - Change:
     - Rewrite every `description` as a **double-quoted single-line scalar**.
       That fixes the six unquoted values containing `: ` and removes the `>-`
       folded scalars from the other eight in one pass.
     - Replace `->` in `superpowers-workflow` with "then".
   - Verify: `yaml.safe_load` succeeds on all 34 files and no frontmatter line
     contains `<` or `>`; run the checker **before** the edit and confirm it
     reports exactly the 6 known failures, so the test is proved to detect the
     defect rather than merely to pass afterwards.

**2. A test that holds every skill to the Agent Skills spec**
   - Files: `tests/test_agent_skills_spec.py` (new)
   - Change: encode the six normative rules from F-2 — frontmatter parses as
     strict YAML; `name` matches `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` with no
     `--`, 1–64 chars, and **equals the parent directory**; `description` is
     1–1024 chars and non-empty; no `<`/`>` in frontmatter; only known keys
     warn-listed. Applies to all three skill roots.
   - Verify: `pytest tests/test_agent_skills_spec.py`; then temporarily restore
     one unquoted description and confirm the test fails.

**3. Vendor the Agent Plugins schemas**
   - Files: `tests/fixtures/agent-plugins-1.0.0-plugin.schema.json`,
     `tests/fixtures/agent-plugins-1.0.0-mcp.schema.json` (new)
   - Change: vendor both documents verbatim, exactly as Tier 1 vendored
     `clispec-v0.3.json`. No new runtime dependency; `jsonschema` is already a
     dev dependency.
   - Verify: both parse as Draft 2020-12 schemas and their `$id` matches the
     `$schema` constant they require.

**4. T3.0 — stop telling agents to call a tool that does not exist**

### Risks & mitigations

- **R1 — Agent Plugins 1.0.0 is 19 days old.** Betting the package's shape on a
  young standard could age badly. Mitigation: `install-agent.sh` stays the
  working install path (A2), so adoption costs nothing if no client implements
  it; the schemas are vendored and pinned, so a revision is a test failure and
  not a silent break; and the format is a superset of what we had — worst case
  it is metadata nobody reads.
- **R2 — Removing `manifest.json` breaks an unknown consumer.** Mitigation: A4
  established there are exactly two, both in-repo. But the file is also
  *documentation* people may have read. Step 8 removes it in the same commit
  that adds `plugin.json`, and `git revert` restores it whole.
- **R3 — The superpowers decision is not mine to make.** It changes what a third
  party receives. It is listed under **Decisions needed** with a recommendation,
  and Phase A delivers value either way — steps 1–5 are correct whichever answer
  is chosen.
- **R4 — Rewriting 34 frontmatters could change a description's meaning.**
  Mitigation: the edit is mechanical (quote the scalar), the parsed value is
  compared before and after, and step 2's test pins the result.
- **R5 — `SNP_MEMORY_ROOT` is a new configuration surface.** A third variable
  next to `SCOUT_AUTH_HEADER` and `--root`. Mitigation: it is a *fallback* for a
  flag that already exists, one mechanism with two entry points, and the refusal
  names it. The alternative — shipping `<path to the memory-system checkout>` —
  is a placeholder that cannot work at all.
- **R6 — Step 5 could change what an existing user's bundle emits.** It will:
  that is the point, because what it emits today cannot authenticate against the
  documented variable. Mitigation: the change is called out in step 9's docs, and
  the test asserts the *new* value rather than merely that something changed.

### Rollback plan

Each phase is a separate commit and nothing later depends on an earlier one's
code:

- **Phase A** is mechanical edits plus two new test files. Reverting restores the
  old frontmatters; nothing else moves.
- **Step 4** is a rename inside documentation and skills. Revertible textually.
- **Step 5** deletes duplicated config in favour of a call. Reverting restores
  the duplication — and the drift with it, which the new test would then catch.
- **Phase C** adds two files and removes one. `git revert` restores
  `manifest.json` exactly; the vendored schemas become unused but harmless.
- **Step 10** is additive: a new command. Reverting removes it.

No migration, no data change, nothing touching the corpus, the vault, or any
running container.

### Decisions needed

1. **Does the superpowers layer ship in `packages/snp-agent`?**
   *Recommended: **no**, and say so explicitly.* The package's job is connecting
   somebody's agent to this memory system — search the wiki, fetch from RAG,
   author pages. The superpowers layer is *this repository's development
   discipline*: it would tell a consumer's agent to write brainstorms and plans
   into their own `artifacts/superpowers/`, for work that has nothing to do with
   the memory system. Declaring it repo-local removes 9 skills, 8 workflows and 7
   instruction files from the distribution surface — and takes 6 broken
   frontmatters off the shipping path — while step 1 still fixes them where they
   actually live. The counter-argument is real and should be weighed: the
   package's own `rules/` references a workflow discipline that would then not be
   there, so if the answer is "ship it", step 6 also syncs `rules/superpowers.md`
   and the 7 instruction files rather than only the skills and workflows.
2. **Adopt Agent Plugins 1.0.0 now (Phase C), or stay bespoke?**
   *Recommended: adopt.* It is metadata, it is cheap, it replaces a manifest only
   our own tests understand, and the `install-agent.sh` path is unaffected either
   way. If the answer is "wait", Phases A, B, D and E still stand and Phase C
   drops out cleanly — nothing else depends on it.
3. **Is `SNP_MEMORY_ROOT` acceptable as the portable pin for the local server?**
   *Recommended: yes, empty by default with a clear refusal.* The alternative is
   omitting the local server from the portable `mcp.json` entirely and leaving it
   to `snpmemory mcp-config`, which already writes it correctly. Both are honest;
   the first keeps the plugin self-describing, the second keeps it minimal.
