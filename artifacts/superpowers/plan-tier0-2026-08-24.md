# Plan — Tier 0: restore the running stack

**Date:** 2026-08-24 · **Branch:** `fix/architecture-security-hardening` (HEAD `2d2b9dd`)
**Scope:** `docs/REMAINING_TASKS.md` Tier 0 (T0.1 … T0.4). Nothing from Tier 1+.

### Goal

The stack can make model calls again, and the failure that took it down cannot
recur silently. Concretely, three things become true and stay true:

1. Every container resolves external hosts, and a host network change no longer
   leaves the stack dead with a misleading error.
2. A model route being unreachable degrades the stack into a *visible*
   `unhealthy` state — it never turns into an unbounded restart loop that
   re-attempts paid work at full speed.
3. `docker compose ps` tells an operator **which** route is down, not just that
   something is.

Non-goals: implementing any of the 14 missing CLI commands, touching the
authoring path, or changing what the stack does when it is healthy.

### Assumptions

- **A1.** The proximate cause of T0.2 is T0.1. Evidence: the sync-job fails with
  `error:EmbeddingError`, and `POST /v1/embeddings` from inside `scout` returns
  500 with `[Temporary failure in name resolution]`. Fixing DNS is expected to
  make the cold start succeed — but the crash-loop defect is independent and is
  fixed on its own merits, not because DNS was down.
- **A2.** `--force-recreate` picks up the host's current nameservers. The host's
  `/etc/resolv.conf` today lists `192.168.2.253` / `192.168.2.235`; the
  containers' baked copy says `NO EXTERNAL NAMESERVERS DEFINED`. **Step 1
  verifies this rather than assuming it** — if recreate does not fix it, the
  cause is upstream of Docker and Step 2 changes shape.
- **A3.** Ingest embeds through the **synchronous** path
  (`scout/ingest.py:259` → `LiteLLMBatchEmbedder.embed_texts` → `urllib`), so a
  DNS failure surfaces as `urllib.error.URLError`, which `_is_transient`
  already classifies retryable. The crash loop is therefore *not* a
  misclassification on this path — it is that in-process retries total 0.75 s
  (0.25 + 0.5) and then the process exits into `restart: unless-stopped`.
- **A4.** LiteLLM 1.95.0 supports `GET /health?model=<group>` and answers `503`
  when that group is unhealthy (observed). Step 8 verifies it answers `200` for
  a healthy group before the health check is switched over — if it does not,
  Step 8 falls back to parsing `/health`'s `unhealthy_endpoints` and filtering
  in the probe.
- **A5.** Publishing model traffic through a specific resolver is a networking
  decision with security implications at a company. The plan therefore does
  **not** hardcode a public resolver into the default compose path; it adds an
  opt-in override. See Risk R2.

### Risks & mitigations

- **R1 — Recreating containers loses state.** `postgres` holds the corpus and is
  *not* in the recreate list (Step 2 names `litellm`, `scout`, `sync-job`
  explicitly). Mitigation: never pass a bare `--force-recreate` without a
  service list; the runbook line documents the same.
- **R2 — Hardcoding a public resolver breaks corporate split-horizon DNS.** An
  internal IT tool that suddenly resolves through `1.1.1.1` may fail to reach
  internal hosts, or may leak internal names to a third party. Mitigation: the
  override is opt-in and unset by default (Step 3); the default path keeps
  Docker's inherited resolvers.
- **R3 — Backoff hides a real outage.** A sync-job that retries forever looks
  alive. Mitigation: readiness stays *cleared* for the whole failing stretch, so
  the health check reports `unhealthy` — the container is alive but honestly
  reporting failure. Step 10's final check proves it.
- **R4 — Loosening the health check lets a genuinely broken proxy start
  ingestion.** Mitigation: Step 8's third verification explicitly tests that a
  broken `snp-embed` still blocks `sync-job`. If that regresses, revert Step 8
  and keep the strict check; the all-or-nothing cost is smaller than the risk.
- **R5 — Step 6 changes the process lifecycle.** A cold start that never exits
  changes what `docker compose up --wait` does on a broken dependency: it will
  now time out rather than see the container exit. Mitigation: note it in the
  runbook alongside the health-check change; the timeout is the correct
  behaviour (the dependency really is down).
- **R6 — A4 may be wrong.** Step 8 verifies it before switching; the fallback is
  in the step itself, so a wrong assumption costs one step, not the plan.

### Rollback plan

Each step is independently revertible and they are ordered so nothing later
depends on an earlier step's *code*:

- Steps 1–2 change no files. Rollback is nothing.
- Step 3 adds a new file and does not modify the default `docker-compose.yml`
  path — deleting `docker-compose.dns.yml` is a complete rollback.
- Step 4 adds a script and its test; delete both.
- Steps 5–7 are one commit in `scout/sync_job.py` plus tests. `git revert`
  restores the previous cold-start behaviour exactly (fail fast + container
  restart). The pre-existing tests are the safety net.
- Step 8 is a `docker-compose.yml` health-check edit; `git revert` restores the
  strict `/health` probe, and R4's verification is the trigger for doing so.
- Step 9(a) is documentation only.

If the stack ends up in a worse state at any point:
`git checkout -- docker-compose.yml scout/sync_job.py && docker compose up -d
--force-recreate litellm scout sync-job` returns to today's behaviour with
today's (working, once recreated) DNS.

## Amendments after the 2026 best-practice review (2026-08-24)

The plan was reviewed against current primary documentation before execution.
Four things changed; the goal and the step order did not.

### AM-1 — `snp-judge` will exhaust its daily quota in ~4 hours (NEW, blocking)

`config/litellm/config.yaml` already sets `background_health_checks: true` and
`health_check_interval: 300`. LiteLLM's docs state `/health` "runs a real test
request against every configured model, so it costs a few tokens per model" —
with background checks on, that cost moves to the background loop, which probes
**every** model group every 300 s. That is **288 probes/day per group**.

`snp-judge` routes to `openrouter/nvidia/nemotron-3-super-120b-a12b:free` on a
free OpenRouter account. OpenRouter's free tier is **50 requests/day** without
$10 of purchased credits. 288 > 50, so the background health loop alone
exhausts the judge quota in roughly **4 hours** — before any actual judging
happens. Then, because the current health check gates on *every* route,
`litellm` goes `unhealthy`, and `sync-job` (`depends_on: service_healthy`)
stops ingesting. A quota meant for `verify-groundedness` would be spent
entirely on monitoring, and it would take down ingestion as it went.

**Amendment to Step 8:** additionally set
`model_info.disable_background_health_check: true` on `snp-judge` and
`general_settings.health_check_skip_disabled_background_models: true`. Both
exist in the pinned LiteLLM 1.95.0 (verified in the installed package at
`litellm/proxy/health_endpoints/_health_endpoints.py:924` and
`proxy_server.py:3379`). The judge is exercised on demand by
`verify-groundedness`, which surfaces its own failures; it does not need a
monitor that costs 6× its daily budget.

### AM-2 — Step 8 must parse the body, not trust the status code

The plan's A4 recorded an **observed** `503` from `/health?model=snp-embed`.
LiteLLM's documentation says `/health` returns **200** with the outcome split
into `healthy_endpoints` / `unhealthy_endpoints`, and documents no unhealthy
status code for the single-model form. Rather than depend on which is true for
this build, Step 8 now **parses `unhealthy_endpoints` from the cached `/health`
response and filters it to the required groups**. `?model=` becomes an
optimisation to adopt only if it proves reliable — not the mechanism.

### AM-3 — Step 6 must cover the watch loop, not only the cold start

Current 2026 guidance for Compose dependencies is explicitly **layered**:
`depends_on: service_healthy` for startup ordering *plus* application-level
retry with backoff, "so a database failover at 3 a.m. doesn't crash
everything." `_async_main` has the same exit-on-failure defect in **both**
paths: the cold start, and the `except SyncFailure` around `watch()`. A
transient embed failure an hour into a watch produces the identical restart
loop. Step 6 now fixes both.

**Why in-app backoff rather than leaning on Docker's:** Docker's restart
backoff starts at 100 ms, doubles to a 1-minute cap, and **resets after the
container runs for 10 seconds**. This container lives well past 10 s (DNS
timeouts are slow), so the backoff resets on every attempt and never
accumulates — which is exactly what 156 restarts at ~19 s intervals looks like.
The orchestrator's backoff cannot help here; the app's must.

### AM-4 — Use `start_interval` on the health checks

`start_interval` (Docker Engine 25.0+, Compose 2.20.2+) probes more frequently
during `start_period` so a healthy container is marked healthy sooner without
loosening steady-state intervals. This host runs Docker **29.7.2** / Compose
**5.5.0**, so it is available. Applied to `sync-job` and `litellm` in Step 8.

### Reviewed and kept unchanged

- **DNS approach (Step 3).** Docker's official networking docs document only
  the per-container `--dns` flag; the wider consensus favours daemon-level
  `/etc/docker/daemon.json` as the "permanent" fix. That file is machine-global
  and affects every unrelated Docker workload on the host, so it cannot ship in
  this repo. The opt-in Compose override stays the repo-shipped answer, and the
  runbook will name `daemon.json` as the host-administrator alternative.
- **Not hardcoding a public resolver.** Unchanged, for the reasons in R2.
- **Fail-fast on `AclPolicyError`.** Unchanged. A missing ACL policy is a
  configuration fault, not a transient one; retrying it forever would be wrong.

### AM-5 — A1 was WRONG: the crash loop has a second, independent cause (deployed image drift)

Step 2 restored DNS and `POST /v1/embeddings` returned `200` with a 1024-dim
vector — but **`sync-job` kept crash-looping with the same
`error:EmbeddingError`**. Assumption A1 ("the proximate cause of T0.2 is T0.1")
is therefore false. Systematic debugging found the real cause:

```
GeminiException BadRequestError - BatchEmbedContentsRequest.requests:
at most 100 requests can be in one batch
```

The corpus document produces **127 chunks**. `scout/chunker.py` splits requests
at `MAX_EMBED_BATCH = 100` precisely to respect that provider cap. But the
running image does not have it:

```
$ docker compose run --rm --no-deps -T sync-job python -c "import scout.chunker as C; print(C.MAX_EMBED_BATCH)"
AttributeError: module 'scout.chunker' has no attribute 'MAX_EMBED_BATCH'
```

The `snp-scout` image was built **2026-08-20T09:57**. The batch-splitting fix
landed in `268af30` at **2026-08-20T15:09** — five hours later — and **14
commits** have landed since the image was built. `docker compose up` never
rebuilds, because only one service carries a `build:` stanza and the rest
reference the `snp-scout` tag directly.

This is bigger than ingestion. `scout` — the MCP server that is the only door
into RAG — is running pre-`268af30` code, i.e. **before** request-scoped auth
and document ACLs. Any "verified live" claim made against this stack since
2026-08-20 was verified against code that is not what the repo contains.

**New Step 2b — rebuild the image, then recreate.** `docker compose build scout`
followed by recreating the services that share the tag.

**New Step 4b — make this drift detectable rather than silent.** `scout/Dockerfile`
carries no `LABEL` and no `ARG`; the image has no
`org.opencontainers.image.revision`, so nothing can tell a stale image from a
fresh one. Stamp the git revision at build time and have the preflight from
Step 4 compare it against `git rev-parse HEAD`, reporting drift as a named
condition instead of a mystery 400 six hours later.
